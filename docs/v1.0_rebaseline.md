# v1.0 Re-baseline — dataset regeneration, stale-result diagnosis, new gate

Living doc for the 2026-06-13 re-baseline. Tracks why the program restarts from Phase 0, what the
regenerated dataset looks like, which prior numbers are stale, and the new μ₀/σ₀/gate once measured.
SSoT for the experiment program stays `training/experiments.md`; project diary stays
`current_working_status.md`.

## Why we are re-baselining

On 2026-06-12 the v2-alpha training data was **destroyed** by an external in-place rewrite of
`gs://abrupt_thaw/RTS_MODEL_V2/DATA/TRAINING_DATA/` (the bucket belongs to the data-production
project; versioning was Suspended → unrecoverable). The data team has since **regenerated both
positive and negative tiles**, bug-fixed and quality-checked. This is not the old dataset restored —
it is a new, materially different and cleaner dataset, so every number tied to v2-alpha is stale and the
program must re-establish its baseline before any ablation can be compared.

Per `data/version.json` upgrade-path and `training/experiments.md §3`, any dataset change requires:
re-run `create_splits` + `compute_normalization_stats`, bump the version, and **re-baseline the
3-seed gate**. We anchor this snapshot temporarily as **v1.0** (a `data/data.md` update from the
user will formalize the version semantics).

### QC pass (user-run, `/mnt/outputs/inference/v21_qc/`)
Per-tile QC over the 1,757 positives in `qc_per_tile.csv`: 9 tiles with a band >50% zero (vs 335 in
v2-alpha), **28 empty-mask positives** (positive class, 0 RTS pixels — a label bug). All 37 flagged tiles
were still present in the live metadata (not yet fixed upstream).

### Cleaning applied for the v1.0 snapshot
- **Dropped 37 positives**: 28 empty-mask + 9 degraded (no overlap) → list in
  `gs://rts-mapping-v2/training/v1.0/dropped_tiles.json`.
- The 28 empty-mask positives are flagged back to the data team as **relabel candidates**
  (`relabel_candidates.csv` in the snapshot) — the correct upstream fix is relabel, not drop, but the
  v0.3 policy is no-relabel so for v1.0 we drop them from training.
- **Cleaned training set: 1,718 pos + 20,541 neg = 22,259 tiles.**

### Separate data-team test set — `TESTING/`
`…/TRAINING_DATA/TESTING/` holds its own `metadata.csv` + PLANET-RGB + labels: **3,000 tiles
(349 pos / 2,651 neg), 22 regions**. All 3,000 tile_ids are **also in the main metadata**, and all 22
regions overlap train regions → it is a designated test subset that is **spatially entangled** with
train. **Open decision (final-lock, §9):** use this as Test-Realistic (accepting region overlap with
train = not spatially independent), or keep carving a spatial-block test split from the main metadata
per `data/data.md §6`. Not baseline-blocking (the gate uses `val_realistic` only). Surfaced at the
post-baseline pause.

## Snapshot staging (reproducibility safeguard)

To prevent another external rewrite from destroying reproducibility, the cleaned dataset is mirrored
into our own project bucket: **`gs://rts-mapping-v2/training/v1.0/`** — cleaned `metadata.csv`,
`PLANET-RGB/`, `labels/`, the `TESTING/` subtree, and `circumpolar_subregions.geojson`. Copy is
server-side via the google-cloud-storage SDK with the user ADC (the gsutil/gcloud CLI auth is broken
on this VM; the SDK works). Script: `scripts/stage_v1_snapshot.py`. `splits.yaml` +
`normalization_stats.json` are generated off the staged snapshot and written back into it.
