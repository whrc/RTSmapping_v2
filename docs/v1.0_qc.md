## Known issues (negatives only) → next-iteration cleanup

Persisted in `gs://rts-mapping-v2/training/v1.0/qc/known_issues_v1.0.json`:
- **49 all-zero (black) negatives** — useless imagery; drop at the next snapshot re-stage.
- **564 degraded negatives** (one RGB band >50% zero, not fully black) — marginal; report to the data
  team for regeneration; drop if not fixed.

**Snapshot-staging correction (positives):** `stage_v1_snapshot.py` dropped 37 positives using the
*stale* mid-drop QC (28 "empty-mask" + 9 degraded). The fresh QC shows only the **9 degraded** were
genuinely bad — the **28 "empty-mask" positives have valid non-empty labels in the current data and
were wrongly dropped** (same stale-QC trap as the batch2 false alarm). **Restore those 28 at the next
re-stage** → target clean positives = **1,746** (not the snapshot's current 1,718). The running
baseline uses 1,718; the 1.6% shortfall is negligible for the gate.

**Decision (user, 2026-06-13):** v1.0 is declared the **standard dataset now**, with these as a
documented minor cleanup. The running Phase-0 baseline is **not** restarted — the 49 black are 0.27%
of the 17,966 train negatives (a trivial-true "black ⇒ not RTS" signal, not a label contamination),
so the gate impact is negligible. The 49 black + 564 degraded are dropped at the next time the
snapshot is re-staged (e.g. when EXTRA lands or a batch is regenerated).
